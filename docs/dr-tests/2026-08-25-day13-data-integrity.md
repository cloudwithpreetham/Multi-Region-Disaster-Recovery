# Day 13 — Post-Failover Data Integrity & Application Verification

**Roadmap task:** Verify data integrity and application functionality post-failover in the secondary region.
**System:** `multi-region-dr` (AWS account 799997637340) — PostgreSQL 16.13 on RDS, primary `multi-region-dr-primary-db` (`ap-south-1`), cross-region read replica `multi-region-dr-secondary-db-replica` (`us-east-1`).
**Status:** Procedure — not yet executed. The system is at steady state post-failback (Day 12), so the promotion-time checks below run either during the next real/simulated failover or, for the replication-health subset, against the current replica now.

## Why this is a separate day from the Day 12 test

Day 12 proved the *mechanism* fires: CloudFront fails traffic over, and the automation promotes the replica. It did **not** prove the promoted database held correct, complete, current data, nor that the application behaves correctly when pointed at it. That is this day's job. The Day 12 report also recorded a split-brain during the application-only simulation (primary DB stayed writable while the replica was promoted); until the Finding 2 guard in `docs/hardening/high-findings-remediation.md` is applied, treat any data written to the primary during a promotion window as at risk of being discarded on failback.

## What "data integrity post-failover" means here

Three distinct claims, verified separately:

1. **Replication was healthy before promotion** — the replica was current with the primary, with bounded lag, at the moment of promotion. This is the one that determines data loss.
2. **The promoted instance is complete and consistent** — after promotion the standalone instance has all committed rows up to the replication cutoff, and no corruption.
3. **The application works against the promoted database** — reads and writes succeed, and application-level invariants hold.

## Part 1 — Replication health (run at steady state, and again right before any planned promotion)

Confirm the replica is actually a replica and measure lag. From AWS:

```bash
aws rds describe-db-instances --db-instance-identifier multi-region-dr-secondary-db-replica \
  --region us-east-1 \
  --query 'DBInstances[0].[StatusInfos,ReadReplicaSourceDBInstanceIdentifier]'
```

`StatusInfos[].Status` should be `replicating` and `Normal=true`. Then the CloudWatch replica lag (seconds the replica trails the primary):

```bash
aws cloudwatch get-metric-statistics --region us-east-1 \
  --namespace AWS/RDS --metric-name ReplicaLag \
  --dimensions Name=DBInstanceIdentifier,Value=multi-region-dr-secondary-db-replica \
  --start-time "$(date -u -d '30 min ago' +%Y-%m-%dT%H:%M:%SZ)" \
  --end-time "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  --period 60 --statistics Maximum Average
```

Record the baseline lag. A healthy cross-region PostgreSQL replica is typically single-digit to low-tens of seconds; a sustained climb means the replica would lose that window of writes if promoted. From SQL, on the **replica**, confirm it is in recovery and see how far behind it is:

```sql
SELECT pg_is_in_recovery();                                  -- expect: t  (before promotion)
SELECT now() - pg_last_xact_replay_timestamp() AS replay_lag; -- time since last replayed txn
```

On the **primary**, inspect the replication slot / WAL sender:

```sql
SELECT client_addr, state, sent_lsn, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS bytes_behind
FROM pg_stat_replication;
```

`bytes_behind` near zero and `state = streaming` is the healthy picture.

## Part 2 — Pre-promotion fingerprint (capture before, compare after)

The reliable way to prove "no data lost in promotion" is to fingerprint the data on the primary at a known point, then confirm the promoted instance matches up to the replication cutoff. Because the schema is application-specific and not known here, parameterize over the real tables — enumerate them, then checksum:

```sql
-- list candidate tables (adjust schema filter to the app's schema)
SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_type = 'BASE TABLE'
  AND table_schema NOT IN ('pg_catalog', 'information_schema');
```

For each business table `<schema>.<table>`, capture a row count and a content checksum. Row count catches missing/extra rows; the checksum catches silently altered rows:

```sql
SELECT count(*) FROM <schema>.<table>;

-- order-independent content hash of the whole table
SELECT md5(string_agg(row_md5, '' ORDER BY row_md5)) AS table_hash
FROM (
  SELECT md5(t::text) AS row_md5 FROM <schema>.<table> AS t
) s;
```

Run this on the **primary** and note the values. If a monotonic column exists (an `id` sequence or an `updated_at`), also record its max — that is your "high-water mark" to check the replica reached.

> Note: on a live system with ongoing writes, primary and replica will never match *exactly* at the same wall-clock instant — the replica trails by the replication lag. Compare the replica against the primary's state **as of the replication cutoff** (freeze writes, or compare high-water marks and accept differences only in rows written after the cutoff).

## Part 3 — Post-promotion verification (run after the replica is promoted)

After promotion, `pg_is_in_recovery()` on the promoted instance returns `f`. Re-run the Part 2 counts/hashes on the **promoted** instance and compare to the primary's pre-promotion fingerprint:

```sql
SELECT pg_is_in_recovery();   -- expect: f  (now a standalone primary)
```

Pass criteria: for every table, the promoted instance's row count and `table_hash` equal the primary's values as of the replication cutoff, and the high-water mark reached at least the cutoff value. Any shortfall is the quantified data loss — record it against the measured `ReplicaLag`, since the two should agree.

## Part 4 — Application functionality against the promoted DB

Mechanism-level (already true if Day 12 passed): the public endpoint returns `200` served from the secondary via CloudFront.

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://dr.cloudwithpreetham.in/health
curl -sI https://dr.cloudwithpreetham.in/health | grep -i x-cache   # expect: Hit from cloudfront
```

Data-plane level (the part Day 12 did not cover): exercise a real read and a real write through the application against the promoted database.

- Perform an application read that hits the DB and confirm it returns data written before the outage.
- Perform an application write, then read it back — confirms the promoted instance is writable and the app has reconnected to it (not still pointed at the old primary).
- Check application logs for connection errors, read-only transaction errors (`cannot execute ... in a read-only transaction` means the app is still hitting a replica, not the promoted primary), or constraint violations.
