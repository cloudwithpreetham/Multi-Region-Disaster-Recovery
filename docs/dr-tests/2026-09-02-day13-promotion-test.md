# Day 13 — Simulated Promotion & Data-Integrity Test (2026-09-02)

**Roadmap task:** Verify data integrity and application functionality post-failover in the secondary region.
**System:** `multi-region-dr` (AWS account 799997637340) — PostgreSQL 16.13 on RDS. Primary `multi-region-dr-primary-db` (`ap-south-1`), cross-region read replica `multi-region-dr-secondary-db-replica` (`us-east-1`). Public endpoint `https://dr.cloudwithpreetham.in`.
**Companion procedure:** `docs/dr-tests/2026-09-02-day13-data-integrity.md` (the reusable "what/why"). This document is the concrete, ordered execution runbook for one controlled promotion, plus a results log to fill in.

## What this test adds beyond Day 12

Day 12 proved the failover _mechanism_ fires (CloudFront fails traffic over, the automation promotes the replica) and it caught a split-brain during an application-only outage. It did **not** prove the promoted database held correct, complete, current data, nor that the application works when writing against it. That is this test's job.

## Why a controlled manual promotion, not the health-check path

The split-brain guard (Finding 2 in `docs/hardening/high-findings-remediation.md`) is **not applied yet**. If we promote by tripping the primary's health check, the Lambda promotes the replica while the primary DB stays writable — a split brain, and the primary keeps taking writes past the replication cutoff, which muddies any "did we lose data" comparison. Day 10 and Day 12 already validated that the SNS → Lambda → `rds:PromoteReadReplica` automation fires. So for a clean data-integrity measurement we promote in a controlled way, with a known write cutoff, and measure loss against that cutoff.

## Safety and prerequisites — read before starting

- **Promotion is irreversible.** Once `multi-region-dr-secondary-db-replica` is promoted it becomes a standalone instance; there is no "un-promote." Restoring the DR posture means rebuilding the replica (the failback in Step 8), exactly as Day 12 did.
- **`psql` client + network path.** The RDS instances are private (`publicly_accessible = false`) and their security group allows the app tier's security group only — your laptop/WSL cannot reach them, and installing `psql` locally does not change that. Run the SQL from inside each region's VPC on an app-tier instance, reached over SSM Session Manager (the instances already carry an SSM role from Day 5):

  ```bash
  aws ssm start-session --target "$ID" --region <region>
  # on the instance (Amazon Linux 2023) — client only, connects fine to the PG16 server:
  sudo dnf install -y postgresql15
  read -s PGPASSWORD; export PGPASSWORD   # paste the password once, hidden (no shell history)
  ```

  Retrieve the password value to paste from `echo "$PGPASSWORD"` on your workstation (it is in Terraform state; do not export it long-term on the shared instance).

Pull it from state into an environment variable without echoing it (see the shorthand block below). Username, DB name, and port come from `describe-db-instances`, not from a tfvars file.

## Step 0 — Confirm steady state (no risk)

Confirm the replica is actually replicating and healthy before you touch anything:

```bash
aws rds describe-db-instances --db-instance-identifier multi-region-dr-secondary-db-replica \
  --region us-east-1 \
  --query 'DBInstances[0].[StatusInfos,ReadReplicaSourceDBInstanceIdentifier]'
```

Expect `StatusInfos[].Status = replicating`, `Normal = true`, and a non-null source identifier. Record the current `ReplicaLag`:

```bash
aws cloudwatch get-metric-statistics --region us-east-1 \
  --namespace AWS/RDS --metric-name ReplicaLag \
  --dimensions Name=DBInstanceIdentifier,Value=multi-region-dr-secondary-db-replica \
  --start-time "$(date -u -d '30 min ago' +%Y-%m-%dT%H:%M:%SZ)" \
  --end-time "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  --period 60 --statistics Maximum Average
```

## Step 1 — Freeze the automation trigger (safety)

So a health flap during the test window cannot trigger an uncontrolled auto-promote, disable the alarm's actions first. The alarm lives in `us-east-1` (Route 53 health-check metrics only exist there — same quirk noted in the Day 10 build):

```bash
aws cloudwatch disable-alarm-actions \
  --alarm-names multi-region-dr-primary-health-alarm --region us-east-1
```

You re-enable this in Step 8.

## Step 2 — Establish a clean write cutoff

The application tier in this project is a **placeholder** — the launch-template user-data just serves a static `ok` health file over `python3 -m http.server` (`terraform/modules/region/asg.tf`) and opens **no** database connection. So there is no application write traffic to freeze; the only writer is you, over `psql`, and the DB is already quiescent at steady state.

To have something concrete to verify across the promotion, seed a marker on the **primary** before the cutoff:

```sql
CREATE TABLE IF NOT EXISTS dr_verify (id serial PRIMARY KEY, note text, created_at timestamptz DEFAULT now());
INSERT INTO dr_verify (note) VALUES ('day13 pre-promotion marker');
SELECT count(*), max(id) FROM dr_verify;
```

Then confirm the replica has received and replayed all WAL up to this point. On the **primary**:

```sql
SELECT pg_current_wal_lsn();
```

On the **replica**:

```sql
SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn(),
       pg_wal_lsn_diff(pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn()) AS unreplayed_bytes;
```

Caught up when the replica's `pg_last_wal_replay_lsn()` has reached the primary's `pg_current_wal_lsn()` and `unreplayed_bytes = 0`, with `ReplicaLag` at 0. That instant is the cutoff.

Scaling the primary app ASG to 0 is **not** needed to freeze writes here — the app never writes. Only scale it down if you also want to exercise the traffic-level failover at the same time, and if you do, run Step 1 first so the alarm cannot auto-promote:

```bash
aws autoscaling update-auto-scaling-group \
  --auto-scaling-group-name multi-region-dr-primary-app-asg \
  --min-size 0 --desired-capacity 0 --region ap-south-1
```

## Step 3 — Pre-promotion fingerprint (on the PRIMARY, at the cutoff)

Enumerate the business tables, then capture a row count and an order-independent content hash for each. Adjust the schema filter to your app's schema:

```sql
-- list candidate tables
SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_type = 'BASE TABLE'
  AND table_schema NOT IN ('pg_catalog', 'information_schema');
```

For each `<schema>.<table>`:

```sql
SELECT count(*) FROM <schema>.<table>;

SELECT md5(string_agg(row_md5, '' ORDER BY row_md5)) AS table_hash
FROM (SELECT md5(t::text) AS row_md5 FROM <schema>.<table> AS t) s;
```

If a table has a monotonic column (`id` sequence or `updated_at`), also record its max — the high-water mark the replica must reach. The `dr_verify` marker from Step 2 will appear in this enumeration; its `count` and `max(id)` are your simplest high-water mark. Record every count and hash in the Results section below. On the replica, confirm it is still in recovery at this point: `SELECT pg_is_in_recovery();` should return `t`.

## Step 4 — Promote (IRREVERSIBLE)

Promote the replica. This exercises the same `rds:PromoteReadReplica` API the failover Lambda calls:

```bash
aws rds promote-read-replica \
  --db-instance-identifier multi-region-dr-secondary-db-replica --region us-east-1

aws rds wait db-instance-available \
  --db-instance-identifier multi-region-dr-secondary-db-replica --region us-east-1
```

`wait` returns once the instance finishes `modifying`/`backing-up` and is `available` as a standalone primary. The endpoint address does not change on promotion. Confirm it is no longer a replica:

```sql
SELECT pg_is_in_recovery();   -- expect: f
```

```bash
aws rds describe-db-instances --db-instance-identifier multi-region-dr-secondary-db-replica \
  --region us-east-1 --query 'DBInstances[0].ReadReplicaSourceDBInstanceIdentifier'   -- expect: null
```

> Optional — to also exercise the automation _code_ (not just the API), invoke the Lambda instead of, or in addition to, the manual call: `aws lambda invoke --function-name multi-region-dr-promote-replica --payload '<event matching the handler>' out.json --region us-east-1`. The Lambda is idempotent (it skips if the target is no longer a replica), so calling it after a manual promote is a safe no-op that proves the guard works. Day 12 already validated the full SNS-triggered chain, so this is optional here.

## Step 5 — Post-promotion fingerprint (on the PROMOTED instance) and compare

Re-run the Step 3 counts and hashes against the promoted instance and compare to the primary's pre-promotion fingerprint:

- **Pass:** for every table, the promoted instance's row count and `table_hash` equal the primary's cutoff values, and the high-water mark reached at least the cutoff value. Because we drained lag to 0 before promoting, the expected data loss is **zero**.
- **Fail / partial:** any shortfall is the quantified data loss — record it against the `ReplicaLag` measured at the cutoff; the two should agree.

## Step 6 — Verify writability and application reachability

**Mechanism level** (already true from Day 12) — the public endpoint serves from the secondary via CloudFront. Note this serves the placeholder `ok` file, which never touches the DB:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://dr.cloudwithpreetham.in/health
curl -sI https://dr.cloudwithpreetham.in/health | grep -i x-cache   # expect: Hit from cloudfront
```

**Data-plane level** — because no app tier connects to the DB, test the promoted instance directly with `psql` (this is the write path a real app would use once deployed):

```sql
-- confirm the pre-promotion marker replicated and survived promotion
SELECT count(*), max(id) FROM dr_verify;          -- must match the primary's cutoff values

-- prove the promoted instance is writable (a replica rejects this)
INSERT INTO dr_verify (note) VALUES ('day13 post-promotion write');
SELECT note, created_at FROM dr_verify ORDER BY id DESC LIMIT 1;
```

A read replica rejects the INSERT with `cannot execute INSERT in a read-only transaction`; a successful insert confirms promotion made the instance writable. The post-promotion row is discarded on failback (Step 8 destroys this instance) — expected.

> **On application-level DB failover:** there is deliberately no app-to-DB wiring in this project yet — the app is the placeholder health server described in Step 2. So "repoint the app at the promoted DB" is out of scope here; there is nothing to repoint. When a real application replaces the placeholder, it must read its DB endpoint from configuration rather than baking in the primary's `ap-south-1` address, so that a promotion actually redirects its writes — that becomes the app-level item to test at that point. Recorded as a follow-up, not a failure of this test.

## Step 8 — Failback / restore the DR posture

The original primary in `ap-south-1` was never lost in this test — it stays authoritative. Rebuild the `us-east-1` instance back into a read replica of it, the same way Day 12 failed back:

```bash
# from the terraform root stack, using the secondary env + the same backend-config key you used on Day 12
terraform apply -replace='module.region.aws_db_instance.replica[0]' \
  -var-file=environments/secondary.tfvars
```

This destroys the promoted instance and recreates a fresh cross-region read replica from the primary. Any row written to the promoted instance in Step 6 is discarded — expected, it was a test write. Note the recreated replica may come up with a **new endpoint address**; if anything references the replica endpoint directly, reconcile it.

Then undo the Step 1–2 safety changes:

```bash
# restore the primary app tier to its previous sizing (see environments/primary.tfvars for the real values)
aws autoscaling update-auto-scaling-group \
  --auto-scaling-group-name multi-region-dr-primary-app-asg \
  --min-size <prev> --desired-capacity <prev> --region ap-south-1

# re-enable the failover automation
aws cloudwatch enable-alarm-actions \
  --alarm-names multi-region-dr-primary-health-alarm --region us-east-1
```

Confirm replication is re-established (`StatusInfos[].Status = replicating`, `Normal = true`, `ReplicaLag` returns to a normal baseline) before calling the system restored.

## Pass criteria

Every business table's row count and content hash on the promoted instance equal the primary's values as of the cutoff (zero data loss, since lag was drained), the pre-promotion `dr_verify` marker is present, the promoted instance is writable (a direct `psql` INSERT succeeds where a replica would reject it), and the failback rebuilds the replica with replication healthy again.
